# Tests

The project has two kinds of tests. They differ in what is real and what is replaced.

| | Unit tests | End-to-end tests |
|---|---|---|
| Run with | `make test` (or `go test ./...`) | `make test-e2e` |
| Needs | Go only | Go and Docker |
| Database | none | real Postgres in a container |
| Location | next to the code (`internal/**/*_test.go`) | `test/e2e/` |

## Unit tests

Fast tests that need nothing but Go. They cover code that can be checked in isolation:

- the order book (matching, price-time priority, partial fills, cancellation);
- the command bus (admission timeout, one send or release per slot);
- the domain entities and the conversion of prices and quantities to integers;
- input validation and HTTP request / response mapping;
- password hashing, JWT issuing and validation, and the configuration checks;
- the use cases, with their repositories and other dependencies replaced by mocks
  (generated by mockery, `make gen`).

## End-to-end tests

They run whole scenarios through the application, from a use case call to the balances,
orders and trades in a real database. Only the entry point differs from a real client: the
tests call the use cases instead of the HTTP API (a *subcutaneous* test, in Fowler's terms),
which lets them control the background processing and read the database directly.

- **Database.** Every run starts a fresh Postgres in Docker (with
  [testcontainers](https://golang.testcontainers.org/)) and migrates it to the same version
  the application uses. The container is removed when the run ends. Each test starts from
  empty tables (only the market data the migrations insert is kept).
- **Real components.** The application is wired as in `cmd/app.go`: the real use cases, SQL
  repositories, command bus, matching engine, event bus and settlement. Nothing is mocked.
- **No HTTP and no frontend.** Tests call the use cases directly, the same way the HTTP
  handlers do. Login and JWT are skipped; a test looks the user up in the database instead.
- **Asynchronous flow.** Placing or cancelling an order only hands a command to the matching
  engine; matching and settlement happen in the background. Tests wait until everything has
  been settled before checking balances and orders.
- **Control over timing.** A test can stop and start the matching engine and settlement, to
  hold commands or events back and set up situations that are otherwise a matter of luck
  (for example two cancels of one order both accepted, or commands lost in a crash before
  they were settled).
- **Configuration.** The tests use the application's own configuration, read from
  `envs/app/.env` (in CI, `envs/app/.env.github_runner`; the database URL is ignored, the
  container provides it). `envs/app/e2e.env` overrides the few values the tests deliberately
  run differently (for example cheaper password hashing, which only affects speed).
  `envs/tests/e2e.env` holds the settings of the tests themselves, such as the size of the
  randomized suite.

The tests share one database and one order book, so they don't run in parallel.

### How a test runs

- `newHarness` empties the tables, builds the components and starts the engine and
  settlement on an empty book.
- Users are registered through the register use case and funded through deposit. The
  harness records every deposit, because the database keeps only the resulting balances
  and the ledger check below needs both.
- *Settled* means the command log is empty and settlement has finished every event the
  engine published. `waitSettled` polls until then, or fails after a timeout. It also fails
  at once if the engine or settlement stopped with an error, which in the app would crash
  the process.
- `mustPlaceOrder` places an order as a setup step, waits until it is settled and returns
  its id. Create returns no order id, so the id is read from the orders table: the new
  order is the one the user didn't have before.
- `restart` simulates a crash: the engine and settlement are stopped and everything in
  memory is thrown away (the book, the commands in the command bus, the events in the
  event bus). The components are then built again on the same database and started the
  way `cmd/app.go` does: settlement first, then the book is loaded, then the engine.
- When a test ends, the harness lets everything settle and runs the state validation
  below. A test that already failed skips it.

### State validation

Every test ends with a check of rules that must hold whatever happened before
(`harness_invariants_test.go`). The randomized suite runs the same check every few
commands. It reads the database directly and needs a settled state: with the command log
empty, the active orders in the database are exactly the book. Every violation is
reported, not only the first.

- **Ledger.** For each user, `main + reserved` of each asset equals the deposits plus the
  effect of the user's trades: the buyer gains the quantity in base and pays the notional
  (quantity × price) in quote, and the seller the opposite. Funds that are created or lost
  anywhere show up here.
- **Reservations.** Each user's reserved funds equal what their active orders still need:
  the remaining quantity in base for an ask, and the remaining quantity × the order's own
  price in quote for a bid. This catches a reservation that isn't released, is released
  twice, or misses the refund after a trade at a better price.
- **Fills match trades.** Every order's filled quantity equals the sum of its trades'
  quantities.
- **Each trade is well-formed.** Both of its orders exist, one is a bid and the other an
  ask, the buyer and seller are the owners of those orders, the quantity is positive, and
  the price lies between the ask and the bid and equals one of them (the resting order's
  price).
- **Status matches the filled quantity.** `0 ≤ filled ≤ ordered`, and: `open` has nothing
  filled, `partially_filled` has some but not all, `filled` has all, and `cancelled` has
  less than all.
- **The book isn't crossed.** The best active bid is below the best active ask; otherwise
  they would have traded.
- **No balance is negative.**

### Test cases

Amounts in the tests are in minor units. The only pair is USD/KCN: USD (base) has 2 decimals,
so 1 USD is 100; KCN (quote) has none. Besides its own assertions, every test checks the
balances of the users involved and ends with the state validation.

**Creating an order** (`create_order_test.go`)

- *Ask reserves the base quantity.* A user with 10 USD sells 3 USD at 7 KCN. 3 USD move from
  available to reserved, and the order is stored as open with nothing filled.
- *Bid reserves the quote notional.* A user with 100 KCN buys 3 USD at 7 KCN. 21 KCN
  (quantity × price) move from available to reserved, and the order is stored as open.
- *Ask without enough base is rejected.* A user with 2 USD tries to sell 3 USD. The use case
  returns "insufficient balance"; nothing is reserved, no command is logged and no order is
  stored.
- *Bid without enough quote is rejected.* A user with 100 KCN tries to buy 3 USD at 50 KCN
  (150 KCN). Rejected the same way.

**Matching** (`matching_test.go`). Each test checks the trades, every order and both
users' balances.

- *No cross: both rest.* An ask of 3 USD at 7 and a bid of 3 USD at 6 don't trade. Both stay
  open and keep their reservations (3 USD and 18 KCN).
- *Equal quantities: both filled.* An ask and a bid of 3 USD at 7 make one trade of 3 USD at
  7. Both orders are filled, the seller receives 21 KCN, the buyer 3 USD, and nothing stays
  reserved.
- *Incoming bigger: the remainder rests.* An ask of 2 USD at 7 meets a bid of 5 USD at 7. The
  trade is 2 USD, the ask is filled, and the bid is partially filled with 3 USD resting and
  21 KCN still reserved for them.
- *Incoming smaller: the resting order is partially filled.* An ask of 5 USD at 7 meets a bid
  of 2 USD at 7. The bid is filled, and the ask is partially filled with 3 USD still reserved.
- *Same price: oldest first.* Asks of 1, 2 and 2 USD at 7 are placed in that order, then a
  bid of 4 USD at 7. The trades are 1, 2 and 1 USD, in placement order, and the third ask is
  left partially filled.
- *A bid sweeps the ask levels.* Asks of 1 USD at 9, 7, 10 and 8 (placed out of price order),
  then a bid of 4 USD at 9. It trades at 7, 8 and 9, each at the ask's own price; the ask at
  10 stays open and the bid rests with 1 USD. The bid reserved 36 KCN, paid 24, got back 3
  (the difference between its price and the ask prices) and keeps 9 reserved.
- *An ask sweeps the bid levels.* The mirror case: bids at 7, 9, 6 and 8, then an ask of
  4 USD at 7 trades with the bids at 9, 8 and 7, at their own prices; the bid at 6 stays open.

**Refund of the excess reservation** (`funds_refund_test.go`). Each user also has a
resting order outside the trade, whose reservation must stay: a refund of everything
reserved would show.

- *A bid that trades at a better ask gets the difference back.* With a resting bid of 2 USD
  at 5 (10 KCN reserved) and an ask of 3 USD at 7, the same buyer bids 3 USD at 8: it
  reserves 24 KCN, trades at 7, pays 21 and gets 3 back. Only the resting bid's 10 KCN stay
  reserved.
- *An ask that trades at a better bid has nothing to refund.* With a resting ask of 2 USD at
  9 and a bid of 3 USD at 8, the same seller asks 3 USD at 7. It trades at 8, so the seller
  receives 24 KCN, not 21. Only the resting ask's 2 USD stay reserved.

**Cancelling an order** (`cancel_order_test.go`)

- *Cancelling an ask releases the base.* A resting ask of 3 USD is cancelled: the order is
  stored as cancelled and the 3 USD are available again.
- *Cancelling a bid releases the quote.* The same for a bid of 3 USD at 7: the 21 KCN are
  available again.
- *Cancelling a cancelled order is rejected.* After the first cancel is settled, a second
  one returns "not cancellable" in the request. No command is logged, and the funds were
  released only once.
- *Two cancels of one order release the funds once.* With the engine stopped, two cancels of
  the same order are both accepted: the order is still active in the database for both.
  The engine removes the order on the first and rejects the second, so the funds are
  released once.
- *Cancelling a partially filled order releases the remainder.* An ask of 3 USD at 7 is
  filled by 1 USD, then cancelled. It is stored as cancelled with 1 USD filled, the seller
  gets the remaining 2 USD back, and the buyer's side of the trade is untouched.
- *Cancelling a filled order is rejected.* The order is no longer active, so the cancel
  returns "not cancellable" and nothing changes.
- *Cancelling an unknown order is rejected.* A random id returns "not found" and no command
  is logged. (Over HTTP the handler still answers 202, so a client learns nothing about
  other users' orders.)
- *Cancelling another user's order is rejected.* Returns "not owned" before anything is
  written; the owner's order stays open with its funds reserved.

**Command bus admission** (`command_bus_test.go`)

- *A full bus rejects the overload.* With the engine stopped, nothing leaves the bus: it
  accepts exactly its capacity (`COMMAND_BUS_BUFFER_SIZE`), and the next orders are
  rejected as overloaded. Only the accepted orders reserved funds and were logged. Once the
  engine runs again, all of them are placed and the bus accepts orders again.
- *A rejected order gives its slot back.* The slot is taken before the funds reservation, so
  an order without enough funds holds a slot it never uses. With the engine stopped and the
  bus one slot short of full, such an order is rejected; the next good order then gets the
  last slot, and the one after it is overloaded. A slot that leaked, or was given back
  twice, would change one of those outcomes.

**Recovery after a crash** (`load_commands_test.go`)

- *Commands the engine never received are replayed.* With the engine stopped, three bids
  that don't cross are accepted: they are only in the command log and the command bus. After
  a restart, which loses the bus, all three are placed from the log, each once and in the
  order they were accepted, and their funds aren't reserved a second time.
- *Commands whose events weren't settled are replayed.* The same with settlement stopped:
  the engine has placed the orders, but their events are lost with the event bus in the
  restart. The replay places each order once.
- *A log longer than the event bus is replayed.* With settlement stopped, the engine fills
  the event bus and blocks, so the log holds one command more than the event bus capacity
  (`EVENT_BUS_BUFFER_SIZE`). Replaying them publishes more events than the bus holds, which
  works only because settlement runs during the load. Before that was fixed, startup hung
  in this situation.

### Randomized suite

`randomized_test.go` checks behaviour that the scenario tests can't spell out: many users
sending commands concurrently with matching and settlement, with crashes in between. The
trades of such a run depend on timing and aren't known in advance, so the state validation
is what is checked.

- **Users.** A few users (`E2E_RANDOM_USERS`), each assigned a random side: they only buy or
  only sell, because the engine doesn't prevent self-trades. Each deposits enough to pay for
  every command at the largest size, so a create never fails for lack of funds.
- **Commands.** A sequence of `E2E_RANDOM_COMMANDS` commands from random users: 30% cancels,
  the rest creates of 1–5 USD at 5–15 KCN. The narrow price range makes orders cross often.
  Commands are sent without waiting for the engine or settlement, so they queue up behind
  each other.
- **Cancels.** A cancel picks one of the user's active orders as they are in the orders
  table at that moment (create returns no order id), or becomes a create if there is none.
  The order may be filled in between, so "not cancellable" is an accepted outcome.
- **Crashes.** Every `E2E_RANDOM_CRASH_EVERY` commands the app is restarted as described
  above, without waiting for things to settle first. Commands still in the bus and events
  not yet settled are lost and must be recovered from the command log.
- **Validation.** Every `E2E_RANDOM_VALIDATE_EVERY` commands, and at the end, the suite waits
  until everything is settled and runs the state validation. The first broken state ends
  the run.
- **Reproducing a failure.** Each run prints its seed. The seed reproduces the users' sides
  and the sequence of commands (users, kinds, quantities and prices); which order a cancel
  picks depends on what was settled by then, so it can differ between runs. A failed run
  writes its steps to `test/e2e/out/randomized-<seed>.log` (in CI, uploaded with the run),
  and setting `E2E_RANDOM_SEED` replays it.

The settings are in `envs/tests/e2e.env`; by default 4 users, 300 commands, validation
every 50 and a crash every 100.
